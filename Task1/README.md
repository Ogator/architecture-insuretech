# Проектирование технологической архитектуры InsureTech

## Требования

- **RTO**: 45 минут
- **RPO**: 15 минут
- **Доступность**: 99.9% (SLA)
- **Текущий объём данных**: 50 GB
- **Требование**: одинаковое время загрузки для всех регионов РФ
- **Требование**: обслуживание клиентов 24/7 из всех часовых поясов

## Архитектурные решения

### 1. Стратегия масштабирования и отказоустойчивости

#### Горизонтальное масштабирование
Горизонтальное масштабирование выбрано как основная стратегия

**Обоснование**:
- Позволяет динамически увеличивать количество pod'ов в Kubernetes при росте нагрузки
- Более экономично для микросервисной архитектуры
- Обеспечивает лучшую отказоустойчивость (отказ одного pod не влияет на доступность)
- Horizontal Pod Autoscaler (HPA) автоматически управляет количеством реплик

**Конфигурация HPA**:
- Target CPU utilization: 70%
- Target Memory utilization: 80%
- Min replicas: 2 (для каждого сервиса)
- Max replicas: 10 (для каждого сервиса)

#### Вертикальное масштабирование
Применяется **избирательно** для PostgreSQL:
- При росте нагрузки на БД увеличиваются CPU/RAM
- Резервируется для случаев, когда горизонтальное масштабирование приложений недостаточно

#### Использование дополнительных зон доступности
**Решение**: Использовать **3 зоны доступности** Yandex Cloud
- ru-central1-a
- ru-central1-b
- ru-central1-c

**Обоснование**:
- Соответствует требованиям SLA 99.9% (допускается ~8.76 часов простоя в год)
- Multi-AZ deployment обеспечивает реальную доступность 99.95%+
- Защита от отказа целой зоны доступности
- Стандартная конфигурация для production-систем

### 2. Конфигурация развёртывания приложения в Kubernetes

#### Решение: 3 независимых кластера

Создать **3 независимых Kubernetes кластера** (по одному в каждой зоне доступности)

**Обоснование**:

**Преимущества независимых кластеров**:
1. **Полная изоляция отказов**: Проблемы в control plane одного кластера не влияют на другие
2. **Независимое управление**: Каждый кластер можно обновлять независимо, минимизируя риски
3. **Простота мониторинга**: Легче выявлять проблемы в конкретной зоне
4. **Рекомендация Kubernetes community**: Multi-region/multi-AZ deployment с независимыми кластерами
5. **Blast radius**: Ограничение радиуса поражения при инциденте

**Почему отклонён растянутый кластер**:
1. **Единая точка отказа**: Control plane становится единой точкой отказа
2. **Сложность управления**: Требует более сложной настройки etcd кластера
3. **Latency между зонами**: Может влиять на производительность control plane
4. **Усложненный troubleshooting**: Сложнее диагностировать проблемы с сетевой связностью

**Дополнительные меры**:
- Единый registry образов (Yandex Container Registry)
- Синхронизация конфигураций через GitOps (ArgoCD/Flux)
- Централизованный мониторинг (Prometheus Federation)

### 3. Балансировка нагрузки

#### Application Load Balancer (ALB)

**Компонент**: Yandex Application Load Balancer

**Функциональность**:
1. **Geo-routing**: 
   - Направление пользователей в ближайшую зону доступности
   - Снижение latency для пользователей из разных регионов РФ

2. **Health Checks**:
   - Интервал: **2 секунды**
   - Количество попыток: **3 retries**
   - Timeout: 1 секунда
   - Unhealthy threshold: 3 неудачных проверки подряд
   - Healthy threshold: 2 успешных проверки подряд

3. **Auto Failover**:
   - Автоматическое исключение нездоровых backend'ов
   - Переключение трафика на здоровые зоны за **4-6 секунд**
   - Возврат трафика на восстановленную зону после прохождения health checks

4. **Rate Limiting для B2B API**:
   - Ограничение запросов от партнёров согласно SLA (например, 20 RPS)
   - Защита от ситуации "один партнёр сжирает все ресурсы"

#### CDN Layer

**Компонент**: Yandex Cloud CDN

**Функциональность**:
- Кеширование статического контента (JS, CSS, изображения)
- Снижение latency для пользователей из удалённых регионов
- DDoS protection на уровне edge locations
- Разгрузка origin servers

#### Health Checks на уровнях

**Схема health checks**:

```
ALB → K8s Ingress → K8s Service → Pods
  ↓         ↓             ↓          ↓
⚕ HTTP    ⚕ TCP       ⚕ TCP    ⚕ HTTP/LivenessProbe
```

1. **ALB Health Checks**:
   - Проверка доступности Ingress endpoints каждого кластера
   - HTTP GET на `/health` или `/healthz`
   
2. **Kubernetes Readiness Probes**:
   - Проверка готовности pod'ов к приёму трафика
   - HTTP GET на `/ready`
   
3. **Kubernetes Liveness Probes**:
   - Проверка жизнеспособности pod'ов
   - Автоматический restart при failure

### 4. Failover-стратегия

#### Стратегия: Active-Active

**Описание**:
- Все 3 зоны **активны одновременно**
- Трафик распределяется между всеми зонами
- При отказе одной зоны трафик автоматически перенаправляется на оставшиеся

**Механизм failover**:

1. **Уровень ALB**:
   - Health check обнаруживает проблему за 2-6 секунд
   - ALB автоматически исключает нездоровую зону из пула backend'ов
   - Трафик перенаправляется на оставшиеся 2 зоны
   - **RTO на уровне приложения**: < 10 секунд

2. **Уровень базы данных**:
   - Patroni обнаруживает недоступность Primary за 10-15 секунд
   - Автоматический failover на Sync Replica за 20-30 секунд
   - **RTO на уровне БД**: < 45 секунд ✅ (соответствует требованию)

**Взаимодействие клиента с приложением при failover**:

```
Нормальная работа:
Client → CDN → ALB → [Zone A (33%), Zone B (33%), Zone C (34%)]

При отказе Zone A:
Client → CDN → ALB → [Zone B (50%), Zone C (50%)]
                       ↑ Автоматическое перераспределение
```

**Особенности**:
- Geo-routing продолжает работать для оставшихся зон
- Session persistence через cookies (опционально, для stateful сессий)
- Graceful degradation: система работает с 2 зонами, но с меньшей пропускной способностью

### 5. Конфигурация базы данных

#### Архитектура: PostgreSQL кластер с Patroni + etcd

**Компоненты**:

1. **PostgreSQL**:
   - **Zone A**: Primary (master)
   - **Zone B**: Synchronous Replica
   - **Zone C**: Asynchronous Replica

2. **Patroni**:
   - Управление жизненным циклом PostgreSQL
   - Автоматический failover
   - Автоматическое переключение ролей (promote replica → primary)

3. **etcd кластер**:
   - Distributed consensus для Patroni
   - 3 узла (по одному в каждой зоне)
   - Обеспечивает координацию и выбор нового primary

#### Репликация данных

**Конфигурация**:

```
Primary (Zone A)
    ├── Sync Replication  → Zone B (synchronous_standby_names)
    └── Async Replication → Zone C
```

**Характеристики**:
- **Synchronous replication** между Zone A ↔ Zone B:
  - Транзакция commit подтверждается только после записи в обе зоны
  - Гарантирует **RPO = 0** для sync replica
  - Защита от потери данных при отказе primary

- **Asynchronous replication** в Zone C:
  - Минимизация latency для write операций
  - Третья копия данных для disaster recovery
  - Потенциальная потеря данных: до 15 минут

#### Backup и Point-in-Time Recovery

**Механизм**:

1. **WAL (Write-Ahead Log) архивирование**:
   - Частота: **каждые 5 минут**
   - Destination: Yandex Object Storage
   - Обеспечивает **RPO = 5 минут** ✅ (лучше требуемых 15 минут)

2. **Полные бэкапы**:
   - Частота: **ежедневно** (в ночное время)
   - Метод: pg_basebackup
   - Retention: **30 дней**

3. **Point-in-Time Recovery (PITR)**:
   - Возможность восстановления на любой момент времени за последние 30 дней
   - Использует полный бэкап + WAL archives

**Достижение RTO/RPO**:

| Метрика | Требование | Реализация | Статус |
|---------|-----------|------------|--------|
| **RTO** | 45 минут | Patroni failover: 30-45 сек<br>Восстановление из backup: 15-30 мин | ✅ |
| **RPO** | 15 минут | Sync replication: 0<br>WAL archive: 5 мин | ✅ |

### 6. Шардирование базы данных

#### Решение: НЕ применять шардирование на текущем этапе

**Обоснование**:

1. **Текущий объём данных: 50 GB**
   - Легко помещается на одном PostgreSQL instance
   - Modern SSD storage обрабатывает такие объёмы эффективно

2. **Преждевременная оптимизация**:
   - Шардирование добавляет значительную сложность
   - Усложняет queries (особенно JOIN'ы через шарды)
   - Усложняет транзакции и обеспечение ACID

3. **Пороговые значения**:
   - Шардирование рекомендуется при **500 GB+**
   - Или при **100K+ write operations/sec**
   - Текущая нагрузка: 50 RPS search + 10 RPS checkout = много ниже порога

**Подготовка к будущему шардированию**:

1. **Архитектура с учётом возможного шардирования**:
   - Логическое разделение схем данных по сервисам
   - Избегание cross-service JOIN'ов в application code
   - Использование distributed transaction patterns (Saga, 2PC)

2. **Возможные стратегии шардирования** (для будущего):
   - **По клиентам**: `shard_key = hash(client_id) % N`
   - **По регионам**: географическое разделение
   - **По типу продукта**: разные шарды для разных страховых продуктов

3. **Подготовка инфраструктуры**:
   - Connection pooler (PgBouncer/Odyssey) уже сейчас
   - Мониторинг query performance и slow queries
   - Tracking роста данных и нагрузки

**Триггер для внедрения шардирования**:
- Объём данных > 500 GB
- Write latency > 100ms P95
- CPU utilization > 80% постоянно
- Невозможность вертикального масштабирования

## Итоговая архитектура

### Ключевые характеристики

| Параметр | Значение |
|----------|----------|
| Количество зон доступности | 3 |
| Kubernetes кластеров | 3 (независимых) |
| PostgreSQL instances | 3 (1 primary + 2 replicas) |
| Стратегия репликации | Sync + Async |
| Failover время (приложение) | < 10 сек |
| Failover время (БД) | < 45 сек |
| RPO | 0-5 минут |
| RTO | < 45 минут |
| Целевая доступность | 99.95% |

### Соответствие требованиям

✅ **RTO = 45 мин**: Patroni failover за 30-45 сек  
✅ **RPO = 15 мин**: WAL archive каждые 5 минут  
✅ **SLA 99.9%**: Multi-AZ обеспечивает 99.95%+  
✅ **Одинаковое время загрузки**: CDN + Geo-routing  
✅ **Обслуживание 24/7**: Active-Active во всех зонах  

### Преимущества решения

1. **Отказоустойчивость**: Отказ любой зоны не приводит к downtime
2. **Масштабируемость**: HPA позволяет автоматически реагировать на нагрузку
3. **Производительность**: CDN и geo-routing снижают latency
4. **Безопасность данных**: Sync replication + регулярные бэкапы
5. **Наблюдаемость**: Централизованный мониторинг и алертинг

### Стоимость vs Надёжность

**Trade-off**:
- 3 зоны вместо 1: увеличение стоимости инфраструктуры в ~2.5-3 раза
- НО: устранение downtime экономит ~500K₽/час × 8.76 часов = **~4.4M₽/год**
- Дополнительно: сохранение репутации и пользователей

**Вывод**: Инвестиции в отказоустойчивость окупаются предотвращением убытков от простоев.
