# Анализ проблем и рисков текущей архитектуры

## Текущая архитектура

### Схема взаимодействия

1. **ins-product-aggregator → Страховые компании**
   - Синхронный REST/SOAP/GraphQL запрос к 5 страховым компаниям при каждом вызове
   - Агрегация результатов в единый список
   - Возврат результата в рамках того же запроса

2. **core-app → ins-product-aggregator**
   - Polling каждые 15 минут
   - REST запрос для получения актуальных продуктов и тарифов
   - Локальная репликация данных в core-db

3. **ins-comp-settlement → ins-product-aggregator**
   - Polling раз в сутки (ночью)
   - REST запрос для получения актуальных продуктов и тарифов
   - Локальная репликация данных в ins-comp-settlement-db

4. **ins-comp-settlement → core-app**
   - Polling раз в сутки
   - REST запрос для получения списка оформленных страховок
   - Использование данных для формирования реестра взаиморасчётов

---

## Проблемы текущей архитектуры

### 1. Синхронная блокировка при агрегации данных

**Проблема:**
`ins-product-aggregator` запрашивает все страховые компании синхронно и блокируется на время ответа самой медленной из них.

**Последствия:**
- Latency агрегатора = max(latency₁, latency₂, ..., latencyₙ)
- При росте до 10 компаний вероятность попадания на медленный/недоступный API удваивается
- Таймауты клиента (`core-app`, `ins-comp-settlement`) ведут к отсутствию данных о продуктах
- Cascade failure: недоступность одной страховой компании блокирует всю выдачу

### 2. Polling вместо push-модели

**Проблема:**
`core-app` опрашивает aggregator каждые 15 минут, `ins-comp-settlement` — раз в сутки.

**Последствия:**
- **Stale data**: данные устаревают между опросами (до 15 минут для `core-app`, до 24 часов для `ins-comp-settlement`)
- **Лишние запросы**: даже если данные не изменились, запросы выполняются по расписанию
- **Пиковая нагрузка**: если несколько клиентов опрашивают одновременно, aggregator получает burst трафика
- При росе до 10 компаний каждый poll-запрос будет ходить в 10 внешних API

### 3. Tight coupling через синхронные REST API

**Проблема:**
Все сервисы связаны синхронными REST вызовами.

**Последствия:**
- **Cascade failure**: падение `ins-product-aggregator` роняет `core-app` и `ins-comp-settlement`
- **Retry storm**: при сбое клиенты будут повторять запросы, усугубляя проблему
- **Невозможность graceful degradation**: нет способа продолжить работу с частично устаревшими данными
- **Backpressure**: нет механизма регулирования нагрузки

### 4. Дублирование логики репликации

**Проблема:**
И `core-app`, и `ins-comp-settlement` самостоятельно запрашивают и реплицируют данные о продуктах.

**Последствия:**
- **Дублирование кода**: логика polling, retry, обработка ошибок написана дважды
- **Inconsistency**: данные в `core-db` и `ins-comp-settlement-db` могут расходиться
- **Увеличение нагрузки на aggregator**: при росте клиентов каждый добавляет свой поток запросов

### 5. Синхронный pull данных о страховках

**Проблема:**
`ins-comp-settlement` раз в сутки запрашивает у `core-app` список оформленных страховок.

**Последствия:**
- **Задержка обработки**: взаиморасчёты обрабатываются с задержкой до 24 часов
- **Batch вместо stream**: все страховки обрабатываются одним батчем ночью, что создаёт пик нагрузки
- **Риск потери данных**: если запрос сорвётся, реестр не будет сформирован
- **Нет real-time мониторинга**: невозможно отслеживать взаиморасчёты в реальном времени

## Риски при росте нагрузки (5 → 10 страховых компаний)

### 1. Удвоение latency агрегатора

**Риск:**
Время ответа `ins-product-aggregator` вырастет пропорционально числу компаний при последовательных запросах, или пропорционально самой медленной — при параллельных.

**Оценка:**
- Сейчас: если каждая компания отвечает за ~500ms, aggregator отдаёт результат за ~500ms (параллельные запросы) или 2500ms (последовательные)
- После роста: ~1000ms (параллельные) или 5000ms (последовательные)
- При параллельных запросах: вероятность попадания на timeout/500-error растёт

**Вероятность:** высокая  
**Влияние:** критическое (SLA нарушается, клиенты видят ошибки)

### 2. Рост частоты ошибок

**Риск:**
Вероятность того, что хотя бы одна из 10 компаний недоступна, выше, чем для 5.

**Оценка:**
- Если каждая компания доступна с вероятностью 99%, то:
  - 5 компаний: доступность агрегатора = 0.99⁵ ≈ 95%
  - 10 компаний: доступность агрегатора = 0.99¹⁰ ≈ 90%
- Без partial failure handling весь запрос падает при недоступности одной компании

**Вероятность:** высокая  
**Влияние:** критическое (частые полные отказы агрегатора)

### 3. Перегрузка сети и CPU

**Риск:**
Polling `core-app` каждые 15 минут означает: 10 запросов к страховым компаниям × 4 раза в час = 40 внешних вызовов/час только от одного клиента.

**Оценка:**
- При 2 клиентах (`core-app`, `ins-comp-settlement`): ~100-200 внешних вызовов/час
- Добавление третьего клиента удвоит нагрузку
- Каждая страховая компания может ввести rate limiting

**Вероятность:** средняя  
**Влияние:** высокое (throttling со стороны страховых, деградация производительности)

### 4. Невозможность масштабирования клиентов

**Риск:**
Если появится новый сервис, которому нужны данные о продуктах (например, мобильное приложение, чат-бот), он добавит ещё один поток polling-запросов.

**Оценка:**
- Каждый новый клиент увеличивает нагрузку на aggregator линейно
- Нет возможности broadcast: каждый клиент получает свою копию данных через отдельный запрос

**Вероятность:** высокая  
**Влияние:** среднее (архитектура не готова к горизонтальному масштабированию)

### 5. Отсутствие observability

**Риск:**
При увеличении числа компаний сложнее понять, какая именно компания вызывает задержки или ошибки.

**Оценка:**
- Нет distributed tracing между aggregator и страховыми компаниями
- Невозможно определить, какая компания отвечает медленно без детального логирования
- Невозможно автоматически отключить проблемную компанию (circuit breaker отсутствует)

**Вероятность:** высокая  
**Влияние:** среднее (увеличение MTTR при инцидентах)

## Рекомендации для устранения проблем

### 1. Переход на Event-Driven Architecture

**Решение:**
Вместо синхронного polling использовать асинхронную доставку событий.

**Архитектурные изменения:**
- `ins-product-aggregator` публикует событие `ProductUpdated` при изменении данных
- `core-app` и `ins-comp-settlement` подписываются на это событие и обновляют локальные реплики
- `core-app` публикует событие `InsurancePolicyCreated` при оформлении страховки
- `ins-comp-settlement` подписывается на это событие для формирования реестра

**Преимущества:**
- Decoupling: сервисы не зависят друг от друга напрямую
- Push-модель: данные доставляются сразу при изменении
- Горизонтальное масштабирование: новые клиенты просто подписываются на события
- Fault tolerance: event broker буферизует события при недоступности клиента

### 2. Использование Transactional Outbox

**Решение:**
Гарантировать атомарность между изменением данных в БД и публикацией события.

**Применение:**
- `core-app`: при создании записи в `core-db` о новой страховке одновременно записывается событие в `outbox` таблицу
- Отдельный процесс (CDC или polling outbox) читает события из таблицы и публикует их в event broker
- `ins-product-aggregator`: при обновлении кэша продуктов также использовать outbox

**Преимущества:**
- At-least-once delivery: события не теряются
- Consistency: нет разрыва между состоянием БД и event stream
- Idempotency: клиенты должны обрабатывать дубликаты

### 3. Асинхронная агрегация с partial failure handling

**Решение:**
`ins-product-aggregator` запрашивает страховые компании асинхронно и возвращает частичный результат, если какая-то компания недоступна.

**Архитектурные изменения:**
- Запросы к страховым компаниям выполняются параллельно с таймаутом
- Если компания не ответила — пропускаем её продукты в текущем цикле
- Публикуется событие с данными от доступных компаний
- Клиенты сами решают, продолжать работу с частичными данными или показать ошибку

**Преимущества:**
- Graceful degradation: система работает даже при частичной недоступности
- Снижение latency: не ждём медленную компанию
- Мониторинг: легко отследить, какая компания недоступна

### 4. Введение Circuit Breaker

**Решение:**
Обернуть каждый вызов к страховой компании в circuit breaker.

**Поведение:**
- Closed state: запросы проходят нормально
- Open state: после N неудачных попыток прекращаем вызовы на время T
- Half-open state: пробуем один запрос, если успешен — возвращаемся в closed

**Преимущества:**
- Защита от cascade failure
- Снижение нагрузки на проблемную страховую компанию
- Быстрое восстановление без ручного вмешательства

## Итоговые метрики

| Метрика | Сейчас (5 компаний) | После роста (10 компаний) | После Event-Driven |
|---------|---------------------|---------------------------|-------------------|
| Latency агрегатора | 500ms (параллельно) | 1000ms | Асинхронно, не блокирует клиентов |
| Доступность | 95% | 90% | 99% (partial failure) |
| Staleness данных | До 15 минут | До 15 минут | Секунды (real-time push) |
| Нагрузка на aggregator | 4 req/hour × 2 clients | 4 req/hour × 2 clients | 0 (только subscribe) |
| Масштабируемость | Линейная по клиентам | Линейная по клиентам | Независимая (fan-out) |
